# Разработка AlreadyMentioned: устройство, запуск и изменение бота

Этот документ описывает **текущее состояние кода**, а не предполагаемые возможности будущих версий. AlreadyMentioned — Telegram-бот на Python 3.12 и aiogram 3. Он работает через long polling, хранит ответы администраторов на вопросы в SQLite и показывает наиболее похожий ответ **из того же чата** в reply с цитатой. Ответы моделью не генерируются, веса модели не обучаются.

## 1. Как устроен проект

```text
Telegram → aiogram Dispatcher (main.py)
             ├─ handlers: команды, обычные сообщения, кнопки
             ├─ services: фильтр вопросов, временная память, embeddings, поиск
             └─ repositories: чтение и запись SQLite
                    └─ database: соединение и схема
```

Зависимости создаются в `main.run()` и передаются обработчикам через механизм внедрения зависимостей aiogram. Один процесс держит одно соединение SQLite, один экземпляр модели (загружается при первом обращении), кэш ответов и кэш подтверждений `/forget`. При остановке соединение и HTTP-сессия закрываются.

| `config.py` | Читает `.env` и переменные окружения. Системные переменные имеют приоритет над `.env`; проверка токена нужна только для запуска бота. |
| `diagnostics.py` | Автономная CLI-диагностика одного вопроса. Открывает существующую БД только для чтения, вычисляет лучшее совпадение и печатает score; в Telegram ничего не отправляет. |
| `bot/factory.py` | Создаёт aiogram `Bot` и HTTP-сессию; берёт HTTPS-прокси из системных proxy-переменных. |
| `bot/permissions.py` | Проверяет статус администратора или владельца через Telegram API. |
| `handlers/start.py` | `/start`. |
| `handlers/solve.py` | Автосохранение reply администратора без сообщения в чат, ручной `/solve`, отмена одного решения через `/undo`. `remember_admin_answer()` временно запоминает reply для ручного сохранения. |
| `handlers/management.py` | `/help`, `/status`, `/threshold`, `/forget` и кнопки подтверждения удаления. |
| `handlers/messages.py` | Обычные текстовые сообщения: фильтрация, запоминание ответа администратора, поиск и reply с цитатой ответа, кнопками оценки и ссылкой на оригинал. |
| `handlers/feedback.py` | Обработка 👍/👎; проверяет, что решение принадлежит текущему чату, и записывает один голос пользователя на показанное предложение. |
| `services/questions.py` | Дешёвый предварительный фильтр русскоязычных вопросов. |
| `services/reply_cache.py` | Оперативная память для reply администратора, необходимая для ручного `/solve`: до 6 часов и 5000 записей. После перезапуска пуста. |
| `services/confirmations.py` | Одноразовые токены `/forget` на 5 минут, привязанные к чату и администратору; после перезапуска теряются. |
| `services/embeddings.py` | Контракт `EmbeddingService`, реализация на FastEmbed и локальной ONNX-модели, нормализация векторов. |
| `services/similarity.py` | Проверенный расчёт cosine similarity для двух векторов. |
| `services/search.py` | Берёт решения одного чата, сравнивает сохранённые вопросы с новым, выбирает максимум и применяет порог чата. |
| `models/entities.py` | Не ML-модель: простые dataclass `Chat`, `Solution`, `Feedback`, возвращаемые репозиториями. |
| `database/connection.py` | Подключение SQLite, создание родительского каталога, `foreign_keys=ON`, ожидание занятой БД до 5 секунд. |
| `database/schema.py` | Создание таблиц и индексов при старте. Сейчас здесь нет механизма миграций существующей схемы. |
| `repositories/chats.py` | Настройки чата, создание/обновление названия, порог, удаление решений чата. |
| `repositories/solutions.py` | CRUD-операции для подтверждённых пар, список по чату, защита от дублирования пары, запись embedding. |
| `repositories/feedback.py` | Сохранение и выборка голосов; повторный голос того же пользователя за то же предложение не добавляется. |
| `__init__.py` в пакетах | Обозначают Python-пакеты; основной логики не содержат. |

В `tests/` лежат автономные тесты соответствующих модулей (`test_config.py`, `test_database.py`, `test_diagnostics.py`, `test_embeddings.py`, `test_management.py`, `test_messages.py`, `test_search.py`, `test_similarity.py`, `test_solve.py`). `tests/fixtures/questions.py` содержит 80 синтетических сообщений для проверки фильтра и поиска. Тесты подменяют Telegram и embeddings; они не измеряют качество настоящей модели на реальных вопросах.

## 2. Поток данных и механика

### Сохранение решения

1. Участник пишет текстовый вопрос в группе. Администратор отвечает на него **через reply** текстовым ответом.
2. `handlers/messages.py` вызывает `remember_admin_answer()`: проверяются тип чата, текст исходного сообщения и права автора. `ReplyCache` временно хранит исходный вопрос, ID сообщений, ссылку и ID администратора.
3. Если исходный вопрос прошёл `is_question_candidate()` и обе ссылки доступны, `autosave_admin_answer()` сразу кодирует вопрос и сохраняет пару **без сообщения бота**. Если фильтр не пропустил вопрос, администратор может ответить на свой ответ командой `/solve` в течение 6 часов: это ручной обход фильтра. Обычная переписка в SQLite не записывается.
4. `EmbeddingService.embed_passage()` кодирует **текст вопроса**, вектор нормализуется и сохраняется как `float32` bytes вместе с текстами и ссылками. Текст ответа нужен пользователю и хранится для учёта, но в поисковый вектор не входит. `/undo` как reply на ответ удаляет сохранённую пару и связанные оценки; бот отвечает только при этой редкой отмене.

Прямые ссылки на сообщения нужны для результата. В обычной группе Telegram их может не быть, поэтому практический сценарий — супергруппа. Privacy Mode бота в BotFather нужно отключить, чтобы он получал обычные сообщения. После рестарта незавершённую reply-цепочку надо создать снова.

### Поиск и голосование

1. `messages.handle_text()` принимает текст в группе или супергруппе от человека, пропускает команды, ботов и ответы администратора, которые были запомнены как потенциальное решение.
2. `is_question_candidate()` требует не менее 7 символов, кириллицу и `?` либо начало с одного из шаблонных выражений (`как`, `где`, `подскажите`, `не работает`, `ошибка` и др.). Это правило может пропускать настоящие вопросы.
3. `SearchService.find_best()` запрашивает решения **только текущего чата**. Если чат ещё не зарегистрирован или решений нет, модель не вызывается.
4. Новый вопрос кодируется с префиксом `query:`. Сохранённые вопросы кодировались с префиксом `passage:`. Поиск сравнивает нормализованные векторы cosine similarity, выбирает один наибольший score и отправляет reply с сохранённым ответом, только если `score >= similarity_threshold`. Текст ответа экранируется для Telegram HTML и показывается в блоке цитаты; свыше 3000 символов он сокращается, а кнопка ведёт к полному оригиналу.
5. Кнопки кодируют ID решения и ID нового вопроса. `feedback` хранит `helpful` или `not_helpful`. Голоса **не меняют** ранжирование, порог или веса модели автоматически.

Если embedding старого решения пустой, поиск пересчитает и сохранит его. Повреждённый вектор при сравнении пропускается. Поиск сейчас линейный по всем решениям чата: каждый запрос загружает список из SQLite и считает сравнение для каждого решения. При большом количестве решений понадобятся замеры и, вероятно, индекс векторов или кэш; произвольную замену алгоритма без проверки качества делать не стоит.

### База данных

| Таблица | Содержимое и ограничения |
| --- | --- |
| `chats` | Telegram ID, название, порог от 0 до 1 (по умолчанию 0.88), дата создания. Порог отдельный для каждого чата. |
| `solutions` | ID чата и двух сообщений, тексты вопроса/ответа, `question_embedding` BLOB, ссылки, дата. Уникальность пары `(chat_id, question_message_id, answer_message_id)`. |
| `feedback` | ID решения, ID вопроса, Telegram ID голосующего, голос, дата. Уникальность `(solution_id, query_message_id, user_id)`. |

Внешние ключи SQLite включены в `connection.py`. `/forget` удаляет решения текущего чата, а связанные оценки удаляются каскадом; сам чат и его порог остаются. Бот не хранит имена пользователей и полную историю переписки. Изменение или удаление исходного сообщения в Telegram не обновляет уже сохранённые тексты и ссылки.

## 3. Установка и запуск

### Локально в PowerShell

Нужны Python **3.12**, интернет для Telegram и первого скачивания модели. Из корня проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
Copy-Item .env.example .env
```

В `.env` заполните `TELEGRAM_BOT_TOKEN=...`, полученный у BotFather. Не публикуйте этот файл. Затем:

```powershell
python -m already_mentioned.main
```

После установки пакета эквивалентна консольная команда `already-mentioned`. Запускать из корня проекта удобно, потому что `.env`, `DATABASE_PATH=data/already_mentioned.db` и каталог кэша модели `models/` сейчас заданы **относительно рабочего каталога**. На Windows используйте Python из `.venv`, а не системный Python другой версии.

### Docker Compose

Нужны Docker Desktop с Linux-контейнерами, Compose и заполненный `.env`:

```powershell
docker compose up -d --build
docker compose ps
docker compose logs --tail 50 bot
```

Остановка: `docker compose stop`; повторный запуск: `docker compose start`; удаление контейнера с сохранением томов: `docker compose down`. Тома Compose содержат собственную БД (`/app/data/already_mentioned.db`) и кэш модели (`/app/models`); они не совпадают с локальными папками `data/` и `models/`. `docker compose down --volumes` удаляет эти тома и данные. При изменении Python-кода пересоберите образ через `docker compose up -d --build`.

Запускайте **один polling-процесс на токен**: одновременно работающие локальный процесс и контейнер будут конфликтовать при получении обновлений Telegram. Если Telegram требует HTTPS-прокси, задайте `HTTPS_PROXY` в `.env`; адрес внутри контейнера должен быть доступен из контейнера (для прокси на хосте Windows часто используют `host.docker.internal`). Публичных входящих портов боту не требуется.

### Настройка Telegram

Создайте бота у BotFather, отключите для него Privacy Mode через `/setprivacy`, добавьте в супергруппу и дайте возможность читать сообщения и отвечать. Для автосохранения, `/solve`, `/undo`, `/threshold` и `/forget` права автора проверяются через `get_chat_member`. Проверить работу можно командами `/start`, `/help`, `/status`, затем вопросом и reply администратора; число решений в `/status` должно увеличиться без служебного сообщения.

## 4. Настройки и диагностика

| Параметр | Где задаётся | Эффект |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | `.env` или переменная окружения | Обязателен для запуска polling; для тестов и диагностики не нужен. |
| `DATABASE_PATH` | `.env` или переменная окружения | Путь SQLite; по умолчанию `data/already_mentioned.db`. Compose переопределяет его на `/app/data/already_mentioned.db`. |
| `HTTPS_PROXY` | Переменная окружения / `.env` | Используется HTTP-сессией Telegram при наличии HTTPS-прокси. |
| Порог совпадения | `/threshold 0.90` в нужном чате | Доступен администратору; число 0–1, допускается десятичная запятая. `/status` показывает текущее значение. |
| Имя и кэш embedding-модели | `services/embeddings.py` | Сейчас `intfloat/multilingual-e5-small`, 384 измерения; локальный кэш `models/`. Это параметры кода, не `.env`. |
| Фильтр вопросов | `services/questions.py` | Минимальная длина, кириллица и вопросительные шаблоны. |
| Время жизни reply и `/forget` | `services/reply_cache.py`, `services/confirmations.py` | Конструкторы по умолчанию: 6 часов/5000 ответов и 5 минут. |

Для исследования конкретной фразы используйте диагностическую команду. Если в БД больше одного чата, обязательно укажите его Telegram ID:

```powershell
.\.venv\Scripts\python.exe -m already_mentioned.diagnostics "Как войти в личный кабинет?"
.\.venv\Scripts\python.exe -m already_mentioned.diagnostics --chat-id=-1001234567890 "Как войти в личный кабинет?"
docker compose exec -T bot python -m already_mentioned.diagnostics --chat-id=-1001234567890 "Как войти в личный кабинет?"
```

Диагностика показывает лучшее совпадение, порог и решение фильтра, но не воспроизводит все условия Telegram-сообщения (reply, права, команда). Она не изменяет БД и не пишет в чат. При первом обращении к модели FastEmbed скачает её; далее вычисления локальные. Для ошибок polling и поиска смотрите `docker compose logs --tail 50 bot` или вывод локального процесса.

## 5. Как изменять механику

**Добавить команду.** Создайте функцию в существующем или новом модуле `handlers/`, зарегистрируйте router в `main.py`, передайте нужные сервисы через аргументы обработчика и зависимости `start_polling()`. Учитывайте порядок роутеров: обработчик текста зарегистрирован после `/solve`, `/undo` и команд управления. Для административной команды вызывайте `is_chat_admin()` и проверяйте тип чата. Добавьте проверку сценария в `tests/` и обновите `/help` и пользовательское руководство.

**Поменять предварительный фильтр.** Правьте `services/questions.py`; затем обновите тесты фильтра и проверьте реальные примеры обычных сообщений, вопросов с ответом и вопросов без ответа. Слишком широкий фильтр увеличит число вызовов модели и ложных подсказок, слишком узкий сделает бота молчаливым. Изменение фильтра не требует пересчёта уже сохранённых векторов.

**Поменять порог или ранжирование.** Порог отдельного чата меняется без кода через `/threshold`. Значение по умолчанию для **новых** чатов находится в `database/schema.py`; изменение `DEFAULT` не перепишет существующие строки. Логику выбора лучшего решения правьте в `services/search.py`, формулу сходства — в `services/similarity.py`. Проверяйте поведение на переформулировках и похожих вопросах с разными ответами. Голоса из `feedback` сейчас доступны через репозиторий, но не подключены к score.

**Заменить модель embeddings.** В `services/embeddings.py` реализуйте контракт `EmbeddingService` или измените `FastEmbedEmbeddingService`; обновите создание сервиса в `main.py` и `diagnostics.py` так, чтобы они использовали **одну и ту же** модель и правила префиксов. Не меняйте только строку `MODEL_NAME`: у другой модели могут быть другие размерность, пуллинг, нормализация, путь ONNX-файла и формат входа. Существующие `question_embedding` нужно пересчитать для **всех** решений до смешанного поиска; одинаковая размерность не гарантирует совместимости пространств. Сначала сделайте резервную копию БД и отдельную миграцию с указанием версии embedding-модели, затем сравните качество на фиксированном наборе примеров. В текущей схеме версия модели для вектора не хранится, а универсальной миграции нет.

**Изменить хранение.** Таблицы описаны в `database/schema.py`, SQL-запросы — в `repositories/`, возвращаемые структуры — в `models/entities.py`. `CREATE TABLE IF NOT EXISTS` не меняет уже созданные таблицы. Для новой колонки или ограничения нужна явная миграция существующей БД и тест как для пустой, так и для старой схемы. Перед изменением или удалением данных сохраните копию SQLite; при активном боте безопаснее остановить процесс и копировать закрытую БД.

**Добавить аналитику оценок или правку отдельного решения.** Данные голосов уже есть в `feedback`, а `/undo` удаляет одну пару по ID исходного ответа. Команды экспорта, статистики и правки пары отсутствуют. Добавляйте SQL в соответствующий репозиторий, проверку прав и команду в `handlers/`. Учитывайте область чата в каждом запросе и то, что ссылки могут устареть после удаления сообщения в Telegram.

## 6. Проверки и практический цикл разработки

```powershell
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты не требуют настоящего токена и не скачивают модель. После изменения поиска дополните синтетические тесты, но отдельно измерьте качество настоящей модели на обезличенных вопросах своего чата: верные переформулировки, похожие по словам вопросы с другим ответом, вопросы без ответа и обычные сообщения. Численный score — мера близости векторов, **не вероятность правильности ответа**.

Для ручной проверки запустите одну копию бота в тестовой супергруппе, вызовите `/status`, ответьте как администратор на подходящий вопрос и проверьте новый счётчик без служебного сообщения, затем отмените ответ через `/undo`. Отправьте похожий и непохожий вопрос, нажмите обе кнопки оценки разными пользователями, проверьте `/threshold` и при необходимости `/forget` в отдельном тестовом чате. Следите за журналом и используйте `diagnostics.py` для точного текста спорного вопроса.

## 7. Текущие ограничения и направления развития

- Это локальный MVP с long polling и SQLite. Нет webhook, нескольких параллельных экземпляров, админ-панели, импорта старой истории и развёрнутой миграционной системы.
- Модель загружается лениво; первое сохранение или первый поиск с решениями может ждать скачивания. Кодирование выполняется в рабочем потоке и защищено lock, чтобы не блокировать event loop и не загружать модель дважды.
- Сохраняются только текстовые вопрос и ответ. Редактирование Telegram-сообщений не синхронизируется с БД. Отдельное решение можно удалить через `/undo` как reply на исходный ответ; правки решения пока нет.
- Оценки сохраняются, но не обучают модель и не меняют выдачу. Для улучшения качества сначала собирайте проверочный набор и измеряйте ошибки, затем меняйте фильтр, порог или модель.
- Большой чат требует оценки скорости линейного перебора решений и объёма SQLite. Переход к векторному индексу имеет смысл после измерения нагрузки и сохранения проверки принадлежности чату.

Краткие правила использования бота для администраторов и участников находятся в [пользовательском руководстве](GUIDE.ru.md).
