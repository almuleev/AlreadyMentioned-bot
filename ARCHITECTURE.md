# Architecture of AlreadyMentioned

Compact map for agents and developers. See [docs/DEVELOPMENT.ru.md](docs/DEVELOPMENT.ru.md) for setup and file details, and [docs/GUIDE.ru.md](docs/GUIDE.ru.md) for user-visible behavior.

## Runtime and boundaries

```text
Telegram long polling
  → main.py: Dispatcher and dependency wiring
  → handlers/: commands, text messages, callback buttons
  → services/: question filter, temporary caches, embeddings, search
  → repositories/: chat, solution, feedback queries
  → database/: SQLite connection and schema
```

`src/already_mentioned/main.py` is the entry point (`python -m already_mentioned.main` or installed `already-mentioned`). It registers routers in this order: `start`, `solve`, `management`, `messages`, `feedback`. It creates one SQLite connection and supplies repositories, search, embedding service, and in-memory caches to aiogram handlers. `config.py` reads `.env` and environment variables. `bot/factory.py` creates the Telegram client, including an HTTPS proxy if configured; `bot/permissions.py` checks chat administrator status.

| Layer | Main files | Role |
| --- | --- | --- |
| Telegram | `handlers/start.py`, `solve.py`, `management.py`, `messages.py`, `feedback.py` | Validate Telegram context and permissions; invoke services and repositories; send messages or callbacks. |
| Search | `services/questions.py`, `embeddings.py`, `similarity.py`, `search.py` | Select likely Russian questions, encode them, compare with saved questions and answers from the same chat, apply the chat threshold. |
| Temporary state | `services/reply_cache.py`, `confirmations.py`, `feedback_cleanup.py` | Hold reply chains for optional `/solve` and `/forget` confirmations in memory; reply/confirmation state is lost on restart. FeedbackCleanup removes keyboards using the persistent SQLite queue. |
| Persistence | `repositories/chats.py`, `solutions.py`, `feedback.py`, `database/connection.py`, `schema.py`, `backup.py`, `models/entities.py` | SQLite access, versioned schema, online backup CLI, and returned dataclasses. `models/entities.py` is not the ML model. |
| Error logs | `error_logging.py`, `handlers/solve.py`, `messages.py` | Record operation, chat/message IDs and error type without message or vector contents. |
| Diagnostics and experiments | `diagnostics.py`, `evaluation.py`, `evaluation_cases.py`, `historical_evaluation.py`, `historical_model_comparison.py`, `reranking_evaluation.py`, `services/reranking.py`, `model_comparison.py`, `offline_training.py`, `public_model_comparison.py`, `candidate_model_comparison.py` | Read-only CLI checks, fixed-case and public-data model comparison, historical scoring/reranking experiments, and public-data adapter training. Experiment outputs are isolated from bot search. |

## Main flows

**Save a solution:** A group member posts a text question → an administrator replies with a text answer → `messages.py` calls `solve.remember_admin_answer()` and stores the candidate in `ReplyCache` → for a question passing `questions.py` and with two direct links, `autosave_admin_answer()` encodes the original question and answer separately and persists the pair silently. The administrator can optionally reply to their own answer with `/solve` within 6 hours to save a question rejected by the filter. Direct message links make supergroups the practical target.

**Suggest an answer:** `messages.py` ignores private chats, bots, commands and non-text messages → `questions.py` filters likely questions → `SearchService` loads saved solutions of the current chat only → `EmbeddingService.embed_query()` encodes the new question → `similarity.py` compares it with each saved question and answer vector → baseline takes the maximum similarity; hybrid reranks the FRIDA top five with MiniLM → the leader is returned only when its active-mode score meets the chat threshold → the handler replies to the new question with the saved answer as an escaped HTML blockquote, one row of 👍/👎 buttons, and a source link in the text (link previews disabled). Only the question author can vote; voting removes the buttons. A background cleanup worker removes unvoted buttons after one hour, checking every 15 seconds and retrying transient Telegram failures. The SQLite queue survives restart; shutdown cancels the worker before closing SQLite and the bot session. The preview is capped at 3000 characters. This is a linear scan of the chat's solutions. Feedback is stored, not used for ranking.

**Manage chat data:** `/status` reads count and threshold; `/threshold` changes that chat's threshold after an admin check. `/solutions` shows a paginated, chat-scoped administrator list with vote totals. `/editquestion ID` and `/editanswer ID` require an admin reply to the stored answer and matching solution ID; each edit recalculates the document embedding of the changed text. `/undo`, sent by an admin as a reply to a saved answer, removes that answer's solution and cascaded feedback; it sends one result message. `/forget` issues an in-memory, one-use token valid for 5 minutes; the same admin must confirm. Deleting that chat's solutions cascades to feedback and clears its pending reply cache. The chat row and threshold remain.

## Data and model contracts

Production defaults to `SEARCH_MODE=hybrid`: FRIDA's five same-chat leaders are scored with pinned MiniLM ONNX using question-plus-answer input, one pair per batch and 512 tokens; final score is 0.75 FRIDA max cosine + 0.25 sigmoid pair score. Reranking is serialized in a worker thread. `SEARCH_MODE=baseline` restores the original decision without re-embedding. Both models warm before polling. SQLite schema 5 adds nullable `chats.hybrid_threshold`; the active hybrid default comes from config, while baseline chat thresholds remain untouched. `/status` and `/threshold` refer to the active mode. Docker installs the `rerank` extra and both pinned caches are required for hybrid startup.

`partial_label_review.py` applies explicit manual F/P/N/U assessments to a versioned historical export, treating substantive partial and full answers as acceptable. It preserves source IDs, dates and author/context fields; unknown labels stay unknown. The owner's revised recall preference uses `--beta 2` for main-early calibration in the search and input experiments. Earlier completeness-based results remain separate.

`SearchService.find_candidates()` exposes distinct same-chat FRIDA solutions before threshold, including separate question/answer similarities, with stable ties and one query encoding. `find_best()` applies the configured baseline or hybrid decision via `rerank_candidates()`. Diagnostics retrieve with `backfill=False`, show raw FRIDA candidates and separately compute the configured decision and threshold without writing SQLite; raw similarity is distinct from the hybrid score.

SQLite has three domain tables in `database/schema.py`: `chats` (chat ID, title, threshold, default `0.88`), `solutions` (question–answer pairs, links and both vector BLOBs), and `feedback` (solution, query message, user and vote), plus the version-3 `embedding_state` contract table and version-4 `feedback_keyboards` cleanup queue (chat/message IDs, question author ID and expiry). The solution repository pages chat-scoped results with vote totals. Foreign keys are enabled. `PRAGMA user_version` adopts validated legacy databases and tracks transactional migrations. `database/backup.py` creates and verifies consistent copies; restoration requires stopping polling. The default database is `data/already_mentioned.db`; Docker uses `/app/data/already_mentioned.db` in a named volume.

Production uses `FridaEmbeddingService`: full FP32 `ai-forever/FRIDA`, pinned revision `850455b605544a944739b25f81ddf812b6e3d0d5`, 1536 dimensions, CLS pooling, 512 tokens, L2 normalization and float32-le storage. New questions use `search_query:`, saved questions and answers use `search_document:`. Single-text CPU inference runs in a serialized worker thread with two Torch threads. Startup warms the model before polling; cache-only loading is the default (`models/`, Docker `/app/models`). `python -m already_mentioned.services.embeddings --download-model` prepares the pinned cache explicitly. Bot and diagnostics share this contract. Legacy FastEmbed E5 remains for reproducible public/model/reranking experiments; its `MODEL_NAME`/`MODEL_DIMENSION` constants refer to E5, not the production default.

Schema version 3 adds `embedding_state`, marking legacy vectors as E5. `database/embedding_contract.py` validates metadata and every persisted vector before polling or diagnostics; an empty database can adopt FRIDA without re-embedding. `python -m already_mentioned.database.reembed DATABASE --backup PATH --bot-stopped` creates and verifies a backup before schema adoption, then recomputes both vectors for all solutions in one exclusive transaction and commits the new contract with them. Failure rolls back vector changes; schema adoption may already be committed. Texts, chat thresholds, links and feedback are preserved. `database/process_lock.py` excludes concurrent new polling/migration processes; old bot versions must be stopped manually. Restoration of E5 vectors requires the old code too. See `docs/FRIDA_MIGRATION.ru.md`.

## Developer entry points

New chats get the provisional application threshold `config.DEFAULT_SIMILARITY_THRESHOLD = 0.458`, passed explicitly by `ChatRepository.ensure_chat`; conflict updates retain the existing threshold. The original SQL default 0.88 remains for legacy schema compatibility, so no table migration is needed. `/status` and threshold confirmations show three decimals. `docs/FRIDA_CALIBRATION.ru.md` records the calibration and its poor late precision; this is an experimental setting, not independent release validation.

- Dependencies, Python version and CLI entry point: `pyproject.toml`.
- Local and Docker launch: `README.md`, `Dockerfile`, `docker-compose.yml`, Windows `start-docker.cmd`; token template: `.env.example`.
- Targeted automated checks: `tests/test_*.py`; full checks: `python -m ruff check .` and `python -m pytest -q` using Python 3.12 and development dependencies.
- Offline quality and ranking timing check: `python -m already_mentioned.evaluation`; it uses fixed fictional cases, production FRIDA, and no Telegram or SQLite access.
- `python -m already_mentioned.threshold_calibration --datasets MAIN PROXY --split-cases CSV --output NEW_JSON` runs production FRIDA on matching local scenarios. It freezes the chronological split before unknown-label exclusion, selects a 0.001-grid threshold only on main early cases using F-beta (default beta 1.1), and applies it unchanged to both later scenarios. It records input/filter/split hashes; labels remain provisional and the later cases have been inspected before. No Telegram or database writes.
- Historical CSV scoring experiment: `python -m already_mentioned.historical_evaluation --cases PATH --banks PATH...`; the CLI uses production FRIDA and records its contract. The reusable `run()` defaults to the legacy E5 report contract for existing offline callers, which must explicitly supply the contract for other encoders. Thresholds/margins are calibrated on earlier cases; JSON reports contain hashes and IDs, no source texts. No bot or database access. E5-only cached reranking refuses FRIDA reports.
- Local historical bank reviews preserve prior snapshots, source-question context and author provenance. Confirmed administrator additions and inferred organizer additions use separate matching case/bank versions. Unpaired announcements and ambiguous answers remain outside the solution bank; reviewed exports do not import solutions into SQLite.
- `docs/LABEL_REVIEW.ru.md` records the October 6 repeat source audit and a separate local candidate label version. It is not independent owner confirmation; prior model metrics refer to version-2 hashes and must not be transferred to revised labels. Private review queues and source evidence stay outside Git.
- Cached historical model comparison: `python -m already_mentioned.historical_model_comparison --model NAME --datasets FOLDER...`; each folder supplies its matching cases and chat banks. One encoder per process, CPU threads limited to two by default, offline cache only. Each scenario selects its threshold on earlier 60% per chat using full F1; later cases, filter misses, warm single-query latency, ranking at 15–200 solutions and process memory are reported separately. No production model, vectors or SQLite changes.
- The committed baseline for the October 3–4 comparison is `docs/experiments/history_models_20261004.json`: aggregate metrics, contracts and input/report hashes without source texts, case IDs or vectors. `docs/HISTORICAL_MODEL_COMPARISON.ru.md` explains that baseline; `docs/FRIDA_QUANTIZATION.ru.md` and `docs/experiments/frida_quantization_20261006.json` record the subsequent paired FP32/INT8 host experiment. Actual VPS resource enforcement remains untested; `docs/NEXT_EXPERIMENT.ru.md` tracks remaining release checks.
- `historical_model_comparison --model frida-int8` applies PyTorch dynamic INT8 conversion to Linear layers in a loaded FRIDA instance, retaining FP32 embeddings and other modules. The source cache and bot stay unchanged. It reports the backend and converted layer count, recomputes all experimental vectors, and samples RSS after individual queries separately from the total peak including cold conversion and passage batches.
- `--passage-batch-size 1` reproduces single-text autosave encoding for quantization comparisons; the batch size is recorded in the experiment contract. Dynamic quantization must be compared with matching encoding batch settings, not assumed insensitive to batch composition.
- Optional `--load-cycles N` measures a serial queue with five same-chat workloads arriving every five seconds, using the longest filtered query per chat and 200 repeated historical solution pairs. It reports complete queue response latency; it is a local inference/ranking simulation, without Telegram, SQLite or actual VPS resource limits.
- Historical top-k reranking: `python -m already_mentioned.reranking_evaluation --cases PATH --banks PATH...`; E5 retrieves candidates before its threshold, then a pinned 8-bit mMARCO MiniLM ONNX cross-encoder scores answer or question-plus-answer pairs on CPU. Both models use two CPU threads by default. Thresholds use earlier cases only. Reports measure candidate coverage, quality, warm latency and process memory; a local CSV queues human review without modifying labels. `--prepare-review-from` prepares review without models using a matching historical report, validating input hashes, embedding contract and case coverage. `--candidates-from --top-k 1` reuses only that report's leaders and measures the reranker alone. The optional `rerank` dependency group supplies inference and memory-measurement libraries.
- Optional model comparison: `python -m already_mentioned.model_comparison`; it uses the same fictional cases, separate embedding spaces, and no production data. The bot model is unchanged.
- Public-data training experiment: `python -m already_mentioned.offline_training`; it learns a diagonal adapter for frozen E5 from a pinned ru-HNP revision and checks held-out data. Outputs go to ignored `training_runs/`; the bot does not load them.
- Public held-out model comparison: `python -m already_mentioned.public_model_comparison`; compares E5, MiniLM and POTION on identical pinned ru-HNP rows, selects each threshold on `val`, and records held-out ranking/classification quality and warm encoding time.
- Extended candidate comparison: `python -m already_mentioned.candidate_model_comparison --model NAME`; runs one of ten Sentence Transformers models at a time on the same pinned ru-HNP rows, selecting the threshold on `val` and measuring CPU query latency. Optional `benchmark` and `benchmark-qwen` dependency groups use different Transformers versions and are isolated from the bot.
- More detailed file inventory, setup, customization and limitations: [docs/DEVELOPMENT.ru.md](docs/DEVELOPMENT.ru.md).
- `python -m already_mentioned.search_experiment --datasets MAIN PROXY --split-cases CSV --output NEW_FOLDER` compares full FP32 FRIDA's existing maximum score, contextual question-plus-answer documents and a cached pinned ONNX reranker over its five leaders. It freezes the chronological split before unknown-label exclusion, calibrates each strategy with F-beta 1.1 on main early cases only, and applies that threshold unchanged to the proxy scenario. Texts/vectors stay out of JSON; candidate IDs and component scores are included for local review. No Telegram or database access; no production ranking change. See `docs/SEARCH_IMPROVEMENTS.ru.md`.
- `python -m already_mentioned.model_results_viewer --reports JSON... --datasets FOLDER...` joins full historical model-comparison reports to hash-matched source CSVs and creates a private standalone offline HTML viewer in ignored `training_runs/model_viewer/`. It compares per-message replies/abstentions, leaders, thresholds, labels and source provenance, with search, error/disagreement filters and a temporary threshold experiment. It loads no models and does not alter reports, labels or bot settings; HTML contains source texts and must stay local. Its bundled HTML template is package data. See `docs/MODEL_RESULTS_VIEWER.ru.md`.

The model-results viewer also displays candidate lists from search experiments and exports/imports manual completeness reviews in a separate hash-bound JSON. These reviews do not change historical labels, displayed metrics or bot feedback/ranking.

`python -m already_mentioned.reranker_input_experiment --candidates-from BASELINE_JSON --datasets MAIN PROXY --split-cases CSV --output NEW_FOLDER` validates source hashes, the full FRIDA contract, question filter and frozen split source before comparing three single-pair ONNX formats, the mean of saved question/answer similarities and a fixed 75/25 FRIDA/reranker blend. It reuses only the baseline's first five candidates, loads no FRIDA, and calibrates thresholds on main early cases only. Outputs join the local viewer; candidate coverage cannot improve and recorded ablation inference costs are not complete strategy/bot latency. See `docs/RERANKER_INPUTS.ru.md`.

That module's `experimental_transport_filter()` helper broadens the existing filter only when both transport and delay/cannot-make-it cues occur; it is not used by the bot or the input-ablation CLI. Local filter experiments recompute previously unscored negatives using full FRIDA and same-chat past solutions, calibrate on main early cases and retain separate report/filter hashes. See `docs/TRANSPORT_FILTER.ru.md`.

The input experiment also accepts `--reranker gte-fp32` for the pinned `onnx-community/gte-multilingual-reranker-base` FP32 export, using the same single-pair ONNX interface and 512-token limit without remote Python code. `--strategies` limits scored formats; `--download-model` explicitly permits downloading pinned files, otherwise loading is cache-only. Model identity and revision are recorded in each report; thresholds cannot transfer between rerankers. See `docs/GTE_RERANKER.ru.md`.

The October 6 FRIDA search experiment on revised provisional labels is recorded in `docs/SEARCH_IMPROVEMENTS.ru.md` and `docs/experiments/search_improvements_20261006.json`. Top-five reranking reduced late errors but lost early correct replies; the main-early recall-count constraint caused many false prompts. These historical experiment variants remain offline; the current production hybrid is calibrated separately under the October 8 partial-answer policy.

Keep this map synchronized with code whenever the flow, component ownership, storage or model contract changes; `AGENTS.md` contains the update rule for every program change.

`release_validation.py` replays the actual SearchService over all rows of an explicit historical export, with only past same-chat solutions, real FRIDA query encoding and optional MiniLM. Unknown labels are executed but excluded from quality metrics; thresholds are supplied, not fitted. It uses no token, Telegram or working SQLite, records joint memory and warm request timing, and can run in an isolated container with real CPU/memory limits. Docker dependency installation is cached separately from source packaging. `docs/TELEGRAM_UX_PLAN.ru.md` is the planned Telegram onboarding/settings work, not shipped UI.
